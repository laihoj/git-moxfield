# ADR 0004: Three ingestion paths into one normalizer (server fetch, browser capture, paste)

- Status: accepted
- Date: 2026-10-09

## Context

Moxfield's API (`api2.moxfield.com`) is undocumented and, as of 2026-10-09, blocked
for server-side clients by Cloudflare (HTTP 403 "Sorry, you have been blocked"),
regardless of User-Agent. Requests from a real browser on `moxfield.com` succeed. The
API sends no CORS headers for other origins, so a git-moxfield page cannot call it
from the browser either. Moxfield's FAQ says the API is private and that personal,
non-commercial projects can ask support for access. Approved projects receive a
dedicated User-Agent.

## Decision

Support three ways to get the current deck. All of them produce the same
`RawSourcePayload` and go through the same validation and normalization:

1. **Server fetch.** `MoxfieldDeckSource.getDeck()` with an honest User-Agent, or the
   Moxfield-issued one from `MOXFIELD_USER_AGENT`. Used for explicit refresh and before
   commit (since ADR 0009 never on page load). A Cloudflare block is detected
   (403 + HTML) and pauses server fetches (since ADR 0009 for every instance, until an
   admin resumes them), so we never hammer the API.
2. **Browser capture.** A bookmarklet generated by git-moxfield runs on the user's
   Moxfield deck page. It fetches the same two endpoints Moxfield's own page uses,
   with the user's browser, and hands the JSON over. Two variants:
   - popup + `postMessage`: `window.open` is called synchronously; the handshake uses
     a one-time nonce in the URL fragment and checks exact origin and source window;
   - same-tab form POST to `/api/capture/form`: for mobile and in-app browsers;
     authenticated by a per-installation **capture token** that git-moxfield bakes
     into this bookmarklet (see "Update" below), with a constant-time comparison.
3. **Manual paste.** Paste the JSON from the two endpoint URLs into `/capture?mode=paste`.

We explicitly do **not** impersonate browsers, run headless browsers, spoof
User-Agents or otherwise evade bot protection.

## Consequences

- Works today without Moxfield's cooperation, and works better (fully automatic) for
  users who obtain a Moxfield User-Agent.
- The capture endpoint receives untrusted data. It is size-limited, schema-validated,
  only updates the observed "working" state (never history), and for untracked decks
  requires an explicit "Track" click.
- The bookmarklet depends on Moxfield's page not sending COOP/CSP that would block it
  (true as of 2026-10-09). The fallbacks (clipboard, same-tab POST, paste) cover
  breakage.
- The same-tab bookmarklet contains a secret and must be reinstalled when the token
  changes (a new database, a revoked token, another installation).

## Update (2026-10-09): token instead of `Origin` for the same-tab POST

The same-tab endpoint first accepted only requests with `Origin: https://moxfield.com`.
A real end-to-end test against live moxfield.com showed that browsers send
`Origin: null` (with `Sec-Fetch-Site: cross-site`) for this form POST: under the
default referrer policy, the origin of a non-CORS POST is hidden when it goes from
https to http, and git-moxfield normally runs on http. Every real capture was rejected.
Because any site can produce `Origin: null` too, accepting it alone would have removed
the CSRF protection. Instead:

- each installation gets a random 256-bit capture token, created atomically on first
  use and stored in the database (`app_settings`), so it survives restarts;
- the setup page embeds it in the same-tab bookmarklet only, which posts it as the form
  field `token`; the endpoint verifies it in constant time and answers 403 without it;
- the `Origin` check stays as defence in depth: `null`, absent, or a configured capture
  origin pass, any other explicit origin is rejected;
- the mock Moxfield's deck page sends `Referrer-Policy: no-referrer`, so end-to-end
  tests see `Origin: null` like real users do.

Details: `docs/moxfield-integration.md`, "Same-tab capture".

## Update (2026-10-10): personal keys and compressed captures

- The per-installation capture token is gone. Every bookmarklet carries its owner's
  personal key instead, in both modes, which decides whose workspace receives the
  capture and signs the browser in ([ADR 0006](0006-accounts-with-bookmarklet-keys.md)).
  Bookmarklets made with the old token must be recreated.
- Both modes compress the capture in the browser before handing it over
  ([ADR 0008](0008-hosting-netlify-and-turso.md)), which keeps it far below the hosting
  platform's request limit; the server decodes it with hard size limits.
- Hosted on Netlify, server fetch is off by default: Cloudflare blocks cloud servers as
  well, so the bookmarklet is how decks arrive.
